学习 Agent 时，我经常遇到 MCP、A2A 和 ANP。这三个名字都与“连接”有关，但面对的对象和问题并不相同：调用一个数据库查询工具、把调研工作交给另一个 Agent、在不同组织之间发现并访问服务，需要不同的约定。

这篇文章整理自我的 Agents Notes，沿着“接入能力 → 委托任务 → 跨域发现与交互”的顺序理解三个协议。这个顺序便于学习，但它们并不是必须依次部署的三层网络栈，功能也存在交集。

## 先看三个协议各自解决什么问题

| 协议 | 主要关注的问题 | 一个具体例子 |
| --- | --- | --- |
| MCP：Model Context Protocol | 宿主如何以统一方式接入工具、资源和提示词模板 | 让 Agent 查询 GitHub 仓库或读取数据库结构 |
| A2A：Agent2Agent Protocol | 独立 Agent 如何描述能力、交换消息、跟踪任务和交付结果 | 将调研任务委托给另一个 Agent，等待报告返回 |
| ANP：Agent Network Protocol | 开放网络中的 Agent 如何描述服务、发现彼此并验证身份 | 找到另一组织的服务，验证请求身份后调用其接口 |

选用哪个协议，取决于系统需要跨越什么边界。一个应用可以同时使用它们，也可以只实现其中一种。

## MCP：把外部能力接入 Agent

### Host、Client 和 Server

从使用者视角，可以把 MCP 理解为宿主和外部服务之间的一套共同语言。正式架构中则要区分三个角色：

- **Host（宿主）**：用户使用的 AI 应用，负责模型集成、上下文组织、权限控制，以及多个连接的管理。
- **Client（客户端）**：由 Host 创建的协议连接组件；每个 Client 与一个 Server 维持独立会话，处理初始化、能力协商和消息交换。
- **Server（服务器）**：提供具体能力的程序或服务，对接文件系统、数据库、Git、业务 API 等。

Host 与 Client 因此不是完全相同的概念：一个 Host 可以管理多个 Client，连接不同 Server。Server 可以是本地进程，也可以是远程服务。

### 三类核心能力

| 能力 | 提供什么 | 通常如何使用 |
| --- | --- | --- |
| **Tools** | 带名称、描述和输入 Schema 的可调用操作 | 模型选择工具并生成参数，宿主执行检查后发起调用 |
| **Resources** | 通过 URI 标识的上下文内容，如文件、数据库表结构或日志 | 应用读取、选择并管理需要提供给模型的内容 |
| **Prompts** | 可复用的提示词模板及其参数 | 用户通过宿主选择模板，用于特定交互或工作流 |

Tools 通常由模型选择，Resources 通常由应用管理，Prompts 通常由用户选择。这描述的是交互分工；宿主仍然决定具体界面、访问策略和上下文组织方式。发现了一项能力，并不意味着它会自动进入模型上下文。

MCP 基于 **JSON-RPC 2.0** 定义应用层消息、生命周期和能力协商。它规范宿主与服务器如何沟通，模型通常只需要看到宿主映射后的工具定义和结果，不需要直接生成 MCP 报文。

### 一次 GitHub 查询如何完成

假设用户要求：“查找与 Agent 相关的 GitHub 项目，按 star 数排序。”可以把调用过程拆成六步：

1. Host 创建 Client，与 GitHub 相关的 MCP Server 完成初始化和能力协商。
2. Client 通过 `tools/list` 获取可用工具；Host 从中选择合适的工具定义提供给模型。
3. 模型根据工具说明生成工具名和参数，例如搜索关键词、排序字段与返回数量。
4. Host 检查参数及权限，再由 Client 通过 `tools/call` 向 Server 发起请求。
5. Server 按自己的业务实现调用 GitHub API，处理认证、限流和错误，将结果返回。
6. Host 把结果交回模型，由模型整理成用户需要的列表。

这里有一个容易混淆的细节：**输入 Schema 由工具提供方定义，模型生成的是符合 Schema 的调用参数。** 模型不负责临时发明服务器的接口结构。

### 统一接口之后，还有哪些工作

MCP 减少了针对不同服务反复编写通信适配的工作，但每个服务的业务逻辑、认证配置、权限范围和错误处理仍然需要落实。把数据库包装成 MCP Server，也不会自动解决查询权限或执行成本的问题。

生态中的现成实现可以作为接入起点；选择时仍需判断其来源、维护状态和实际权限需求：

- [MCP Registry](https://registry.modelcontextprotocol.io/)：官方服务器注册表。
- [MCP 参考服务器](https://github.com/modelcontextprotocol/servers)：由 MCP steering group 维护的参考实现；仓库说明这些实现主要用于演示和教学。
- [Awesome MCP Servers](https://github.com/punkpeye/awesome-mcp-servers)：社区维护的服务器集合。

当现有服务不适合内部业务时，也可以编写自己的 MCP Server，用它封装私有数据访问、内部微服务或定制操作。

## A2A：让独立 Agent 协作

### 从调用操作到委托工作

工具调用通常围绕一个明确操作展开，例如“查询仓库”。协作任务可能更开放：把“比较几个 Agent 框架并给出报告”交给研究 Agent，由它自行决定内部步骤，再返回过程状态和最终结果。

A2A 规定这类独立 Agent 之间如何交换能力描述、消息、任务状态和产物，而不要求对方暴露内部提示词、记忆或工具链。同一个 Agent 在不同交互中可以分别充当请求方和服务方。

### Task、Artifact 与 Agent Card

| 概念 | 含义 |
| --- | --- |
| **Agent Card** | Agent 的描述文档，包括能力、接口及安全相关信息，供请求方了解如何交互 |
| **Message** | 一次通信中的消息，可承载用户请求或 Agent 回复 |
| **Part** | 消息或产物中的内容单元，用于表达文本、文件或结构化数据等内容 |
| **Task** | 可跟踪状态的工作单元，适合需要持续执行或多轮交互的任务 |
| **Artifact** | 任务产生的交付物，例如报告、文件或结构化分析结果 |

“帮我做调研”是一条请求消息；执行过程中产生的工作可以表示为 Task；最终报告是 Artifact。简单交互也可以直接返回 Message，不需要每次都创建任务。

不能把“有没有 Task”当作 MCP 和 A2A 的绝对分界。MCP 在 **2025-11-25** 规范中也加入了实验性的 Tasks。更有用的区别是：MCP 主要关注外部能力与上下文接入，A2A 主要关注独立 Agent 之间的协作语义。

### 任务生命周期与请求流程

对于持续执行的任务，请求方需要知道它是否仍在处理、是否等待补充材料，以及最终是否成功。A2A 定义了已提交、处理中、需要输入、需要认证、完成、失败、取消和拒绝等状态语义。其中“需要输入”或“需要认证”意味着交互可能继续，完成、失败、取消和拒绝则属于终态。

一次交互通常包括：

1. **发现与读取描述**：取得目标 Agent 的 Agent Card，了解其能力、支持的接口和交互方式。
2. **满足认证要求**：按照服务声明的安全机制获得所需凭证，并满足服务端的访问策略。
3. **发送请求**：按能力与需求选择普通请求/响应，或者流式交互。两者是可选方式，不是每次请求都必须依次执行的两个阶段。
4. **跟踪并接收结果**：接收消息、任务状态和产物更新；若需要补充输入，则围绕相应任务继续交互。

这样，研究 Agent 可以先返回“正在检索”，再请求限定时间范围，最后交付报告。调用方无需一直等待一个不透明的长请求，也不必了解研究 Agent 的内部实现。

### A2A 不规定整个系统的拓扑

常见多 Agent 系统由一个主 Agent 分派任务并汇总结果。这种中心编排可能带来瓶颈或单点故障，但它也便于控制流程和审计。

A2A 允许独立 Agent 通过统一协议交互，**并不要求所有节点组成 P2P 网状网络，也不会自动消除中心瓶颈**。官方介绍中同样有由一个 assistant 编排其他 Agent 的例子。是否保留主 Agent、是否允许直接通信，以及如何容错和扩容，仍是系统设计问题。

## ANP：面向开放网络的发现与身份

### 跨平台之后，先解决“找到谁、如何访问”

当服务分布在不同组织、域名和平台时，请求方未必预先知道目标是谁、能做什么、接口在哪里，双方也未必共享同一套账户体系。

**ANP 的全称是 Agent Network Protocol。** 它围绕开放网络中的身份认证、描述与发现等机制，帮助 Agent 获取理解和访问另一服务所需的信息。这里的发现和描述可以为选择提供依据；按实时负载、价格或质量选出最合适的服务，仍然需要应用自己的策略。

| 概念 | 在交互中的作用 |
| --- | --- |
| **Agent Description** | 描述 Agent、可提供的信息及接口，让请求方知道如何访问能力 |
| **发现入口与索引** | 公开描述文档的位置；搜索服务可以据此建立索引 |
| **DID 与 DID 文档** | 标识身份，并提供验证身份相关签名所需的公钥等信息 |
| **接口描述** | 说明服务调用方式与数据结构，支撑跨系统交互 |
| **应用选择策略** | 根据能力及可获得的业务信息选择服务，属于应用层设计 |

### 从发现到调用的一个例子

以下按 `did:wba` 的思路说明 Agent A 如何访问 Agent B：

1. **B 发布描述入口。** `/.well-known/agent-descriptions` 公开 Agent Description 的地址集合；具体描述再链接到能力和接口信息。
2. **A 找到目标。** A 可以从已知域名开始发现，也可以查询收录这些描述的搜索服务。搜索索引是一种实现方式，并非唯一入口。
3. **A 读取描述并准备请求。** A 根据 B 的接口说明构造调用；对于需要认证的请求，按约定使用与自身 DID 对应的密钥签名。
4. **B 验证身份与请求。** B 解析 A 的 DID 文档，获取对应公钥并验证签名及相关请求校验信息。
5. **B 检查权限并执行。** 服务端继续检查业务权限及必要的用户授权，随后执行操作、返回数据或结果。

{{< fig src="figures/anp-discovery.zh.svg" alt="ANP 发现与调用示意：Agent B 发布描述，Agent A 发现并读取接口，发送签名请求，B 解析 A 的 DID 验签并检查业务权限。" caption="以 did:wba 为例的 ANP 交互。发现、身份认证与业务授权分别解决不同问题。" >}}

签名验证有助于确认身份和请求完整性，但不能单独证明服务质量、业务权限或用户对某项操作的同意。即使知道“请求来自 A”，B 仍然需要判断“A 是否可以执行这项操作”。

ANP 可以降低对单一 Agent 平台或统一身份账户的依赖，但不能据此推导出完全没有基础设施依赖。`did:wba` 路线仍建立在域名、HTTPS 和相关 Web 信任基础之上。

## 三者如何在一个系统中配合

以“调研 Agent 框架并生成报告”为例，可以设想这样的组合：

- 本地研究 Agent 通过 **MCP** 调用 GitHub 搜索、读取文件或查询内部数据库。
- 主 Agent 通过 **A2A** 把一部分分析委托给另一个专业 Agent，跟踪任务并收取报告产物。
- 面对事先没有接入的外部服务时，应用通过 **ANP** 的描述、发现与身份机制找到目标，并按其接口交互。

这是一种应用架构示例，不表示三个协议天然串联或可以直接互换。若两端采用不同协议，仍需要应用明确衔接方式、数据映射和访问控制。

对我来说，理解它们最有用的方式是先追问实际问题：需要统一工具接入时看 MCP，需要委托独立 Agent 并跟踪工作时看 A2A，需要跨域发现与身份交互时看 ANP。协议帮助双方对接口达成一致；调度策略、容错、业务权限和结果质量，还需要系统本身负责。
